# Кейс-задача № 5. Запуск и мониторинг — анализ

Проект: https://github.com/fatmilkkk/unity-game-release-monitoring

**1. Выбор платформ выпуска.**
Для выпуска выбраны три платформы. Windows (x64) — основная аудитория ПК, распространение через itch.io и GitHub Releases. Браузер (WebGL) — игра запускается без установки, что снижает порог входа; площадки — itch.io и Яндекс Игры. Android — мобильная аудитория; APK используется для тестов, AAB — для Google Play и RuStore. Выбор опирается на результаты предыдущего этапа: игра уже адаптирована под сенсорное управление, вырезы экрана и разные разрешения. Неподдерживаемые элементы скрываются автоматически: кнопка «Выход» в браузере, полноэкранный режим на телефоне. Платформы, их форматы и обоснование зафиксированы в чек-листе релиза (Docs/Release/RELEASE_CHECKLIST.md).

**2. Автоматизация сборки.**
Написан инструмент ReleaseBuildTool (меню Tools → Release). Он собирает Windows, Android (APK или AAB), WebGL или все платформы сразу, а также Development-сборку для отладки. Перед сборкой инструмент проверяет, установлен ли модуль платформы, и выдаёт понятное сообщение с инструкцией, если нет. Если сцены ещё не созданы (чистый клон, CI), он генерирует их, а затем настраивает платформу. Для Android задаются идентификатор пакета com.portfolio.ballcollector, минимальная версия API 23, IL2CPP и архитектуры ARM64 + ARMv7: Google Play требует 64-битные сборки. Для WebGL — сжатие Brotli с запасным распаковщиком (работает на хостингах без нужных HTTP-заголовков) и кэширование данных. Результат раскладывается по папкам Builds/<платформа>/v<версия>/. Сборка одной командой исключает ручные ошибки: забытую сцену, неверную платформу, незаполненную версию.

**3. Управление версиями и информация о сборке.**
Используется семантическое версионирование MAJOR.MINOR.PATCH; текущая версия — 1.2.0. Каждая сборка получает растущий номер (ProjectSettings/BuildNumber.txt). Для Android versionCode вычисляется из версии (1.2.0 → 10200), поэтому всегда растёт, как требует магазин. Перед сборкой создаётся файл Resources/build_info.json: версия, номер сборки, дата UTC, короткий хэш коммита Git (читается из папки .git без запуска git), платформа и признак Development. Эти данные видны в главном меню и автоматически попадают в отзывы и события аналитики. По сообщению игрока можно точно определить, на какой сборке возникла проблема, и найти соответствующий коммит.

**4. Отчёты о сборке и непрерывная интеграция.**
После каждой сборки сохраняется отчёт Builds/<платформа>/build_report.txt: результат, размер, время, число ошибок и предупреждений, коммит. В общую таблицу Builds/build_history.csv добавляется строка, по которой можно отслеживать рост размера сборки от версии к версии. Для автоматизации подготовлен сценарий GitHub Actions на основе GameCI (.github/workflows/build.yml). Он запускает EditMode- и PlayMode-тесты, собирает Windows, WebGL и Android через ReleaseBuildTool.BuildFromCommandLine, сохраняет сборки как артефакты, а при публикации тега вида v1.2.0 создаёт GitHub Release с архивами и автоматическим списком изменений. Сценарий запускается вручную или по тегу и требует лицензии Unity в секретах репозитория: порядок их добавления описан в комментарии к файлу.

**5. Материалы для публикации и юридическая подготовка.**
Подготовлены материалы для страницы игры (Docs/Release/STORE_LISTING.md): название и описания на русском и английском (короткое до 80 символов и полное), ключевые слова, жанр, возрастной рейтинг 6+ / PEGI 3, список из семи скриншотов с разрешениями, требования к иконке. Отдельно составлена политика конфиденциальности (PRIVACY_POLICY.md): она обязательна для магазинов приложений при сборе любых данных. В политике перечислено, что собирается и что не собирается, где хранятся данные, как отказаться от сбора и удалить их. Журнал изменений (CHANGELOG.md) ведётся по всем версиям проекта, от 1.0.0 до 1.2.0. Чек-лист релиза разбит на этапы: перед сборкой, сборка, проверка сборок на каждой платформе, публикация и действия в первые 7 дней.

**6. Система аналитики и согласие игрока.**
Реализована собственная анонимная аналитика (AnalyticsService) без сторонних SDK. При первом запуске игроку показывается окно согласия с объяснением, что собирается и что нет; до ответа ни одно событие не записывается. Решение можно изменить в настройках, а при отказе уже собранные локальные данные удаляются. Каждой установке присваивается случайный идентификатор, личные данные не собираются. События пишутся построчно в JSON (events.jsonl) с буферизацией: файл сбрасывается каждые 10 событий, сразу после ошибок и завершения уровня, а также при сворачивании приложения — на мобильных оно может быть выгружено без штатного выхода. Файл ограничен 2 МБ, затем архивируется. Если в удалённом конфиге указан сервер, события отправляются пачками POST-запросом с повтором при ошибке сети.

**7. Какие данные собираются и зачем.**
События подобраны под вопросы, на которые разработчику нужен ответ. session_start и session_end — устройство, ОС, видеокарта, память, экран, длительность сессии: кто играет и сколько. level_start и level_end с результатом (победа, гибель, выход без завершения), временем, монетами и звёздами показывают, сколько игроков проходит уровень. Вехи progress (25, 50 и 75 % монет) строят воронку прохождения и показывают, на каком участке игроки сдаются. death — причина (препятствие, бочка, осколки взрыва, падение) и координаты: что именно убивает игроков и где. bonus_found и item_used показывают, используют ли игроки предметы. perf — средний FPS каждые 30 секунд с уровнем качества и разрешением, то есть реальная производительность на устройствах игроков. Для этого источник урона теперь сохраняется в PlayerHealth (LastDamageSource).

**8. Сбор ошибок.**
CrashReporter перехватывает все исключения и ошибки через Application.logMessageReceived. Каждая уникальная ошибка (тип + текст + первая строка стека) отправляется в аналитику один раз за сессию — иначе ошибка в Update засыпала бы файл тысячами одинаковых записей. В конце сессии записывается сводка: сколько уникальных ошибок и сколько всего повторов. Последние пять ошибок прикладываются к отзыву игрока, если он отметил «Приложить техническую информацию». Так разработчик узнаёт об ошибках, даже если игрок о них не сообщил, и сразу видит место в коде.

**9. Сбор отзывов игроков.**
Окно отзыва открывается из меню паузы и с экранов победы и поражения — в моменты, когда у игрока есть впечатление. В нём оценка от 1 до 5 звёзд, тип обращения (отзыв, ошибка, предложение), многострочное поле текста и флажок технической информации (версия, сборка, коммит, ОС, устройство, видеокарта, настройки графики, последние ошибки). Отзыв сохраняется локально, оценка и категория попадают в аналитику. Затем в браузере открывается страница нового обращения GitHub Issues с заполненным заголовком, текстом и меткой (bug, feedback или enhancement). Так отзывы попадают в трекер задач разработчика без собственного сервера. Для игроков, которые пишут напрямую на GitHub, созданы шаблоны обращений с полями версии, платформы и шагов воспроизведения. Пока игрок печатает, игровые клавиши (I, Tab, цифры) отключены.

**10. Анализ статистики: панель в редакторе.**
Для анализа создана панель Tools → Release → Analytics Dashboard. Она читает события из папки данных игры и из папки AnalyticsData проекта, куда складываются файлы тестировщиков. Повреждённые строки (например, после аварийного завершения) пропускаются и подсчитываются. Панель показывает аудиторию (установки, сессии, средняя длительность, версии и платформы), долю прохождения, воронку из пяти шагов с полосами, причины гибели, использование предметов, средний FPS и долю замеров ниже 30, топ ошибок, среднюю оценку и последние отзывы. Места гибели отображаются в окне Scene поверх уровня тепловой картой: чем больше гибелей рядом, тем крупнее и краснее отметка. Опасные участки видны сразу. Отчёт можно выгрузить в Markdown, сессии из редактора можно исключить, чтобы тесты разработчика не искажали статистику. Для проверки самой панели есть генератор демонстрационных данных; они явно помечены как сгенерированные, и панель показывает предупреждение, пока они загружены.

**11. Автоматические рекомендации по результатам анализа.**
Модуль AnalyticsAggregator превращает метрики в задачи на обновление по набору правил. Если прохождение ниже 30 %, уровень считается слишком сложным; выше 90 % — слишком простым. Если бочки — причина более 40 % гибелей, он предлагает поднять порог взрыва и указывает текущее значение. Также он предлагает снизить урон препятствий, если они главная причина гибели, и добавить ограждения при частых падениях. Он находит шаг воронки с наибольшим оттоком и сигнализирует, если более 30 % попыток брошено. По звёздам он предлагает ужесточить норматив, если более 80 % побед на три звезды, или смягчить, если таких побед менее 10 %. Отдельно он отмечает, что игроки гибнут, но не используют аптечки, а также низкий FPS, самую частую ошибку и среднюю оценку ниже 3,5. Если запусков меньше 10, выводы явно помечаются как предварительные, чтобы не менять игру по случайной выборке. Правила покрыты автотестами.

**12. Обновление без выпуска новой версии: удалённый конфиг.**
Часть проблем, найденных аналитикой, можно исправить в тот же день без пересборки. Игра при запуске загружает файл Config/remote_config.json из репозитория по ссылке raw.githubusercontent.com. В нём заданы порог скорости взрыва бочки, множитель урона препятствий, нормативы времени для звёзд, новости, последняя версия со ссылкой на обновление, адрес сервера аналитики и репозиторий отзывов. Последний удачный конфиг кэшируется: без интернета действует он, а при первом запуске — встроенные значения, совпадающие с исходным балансом. Некорректный JSON игнорируется, значения вне безопасных диапазонов ограничиваются. Ошибка в конфиге не может сломать игру, например порог взрыва ниже 2 м/с невозможен. Версия конфига записывается в события начала уровня, поэтому эффект изменения баланса можно сравнить на данных до и после.

**13. Информирование игроков об обновлениях.**
В главном меню появились карточка новостей, текст которой меняется через удалённый конфиг (например, анонс версии или события), и уведомление «Доступна версия X (у вас Y)» с кнопкой «Обновить». Оно показывается, если в конфиге указана версия новее установленной; версии сравниваются семантически (1.10.0 новее 1.2.0). Нажатия на кнопку обновления учитываются в аналитике. После обновления игры один раз автоматически показывается окно «Что нового» со списком изменений версии — но не поверх запроса согласия, а после него. Номер версии и сборки всегда виден в углу главного меню, чтобы игрок мог указать его в отзыве.

**14. Процесс работы с обратной связью и пример обновления.**
Процесс оформлен как цикл (Docs/Release/LIVEOPS.md). Первый шаг — сбор данных 3–7 дней после выпуска. Затем анализ в панели и группировка отзывов по темам. Потом приоритизация: критические ошибки — немедленная patch-версия, баланс — правка конфига в тот же день, интерфейс и механики — следующая minor-версия. Далее задача в GitHub Issues, исправление, автотесты, сборка, выпуск с обновлённым «Что нового» и latestVersion, и наконец проверка эффекта по сравнению версий в панели. В документе приведена таблица соответствий «наблюдение → порог тревоги → действие». Например, если более 40 % гибелей происходят от бочек, порог взрыва поднимается с 7 до 8,5 м/с через конфиг. Если прохождение ниже 30 %, урон препятствий снижается до 0,8.

**15. Тестирование новых систем и выводы.**
Новые системы покрыты 29 дополнительными EditMode-тестами (всего в проекте их 71). Тесты проверяют сравнение версий, разбор и ограничение значений удалённого конфига, корректность файла конфига в репозитории, сериализацию событий, пропуск повреждённых строк, подсчёт метрик и воронки, исключение сессий редактора, срабатывание рекомендаций, отсутствие записи без согласия, кодирование ссылки на GitHub, дедупликацию ошибок и наличие версии сборки. В результате игра подготовлена к выпуску на три платформы, а замкнутый цикл «выпуск → сбор данных и отзывов → анализ → изменение баланса или новая версия → проверка эффекта» реализован инструментами в самом проекте. Дальше можно подключить собственный сервер сбора (адрес указывается в конфиге без изменения кода), настроить подписание Android-сборок для Google Play, добавить A/B-тесты баланса через конфиг и автоматическую публикацию сборок на itch.io через butler.
